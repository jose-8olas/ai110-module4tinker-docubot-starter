# DocuBot Model Card

This model card is a short reflection on your DocuBot system. It describes the implementation of retrieval and experiments with all three modes:

1. Naive LLM over full docs
2. Retrieval only
3. RAG (retrieval plus LLM)

---

## 1. System Overview

**What is DocuBot trying to do?**

DocuBot is a documentation assistant designed to help developers find answers to questions using project documentation. It uses retrieval and large language models to provide relevant information while reducing unsupported answers. It supports three modes: Naive LLM, Retrieval Only, and Retrieval-Augmented Generation (RAG).

**What inputs does DocuBot take?**

DocuBot takes the following inputs:

- A user's natural-language question.
- Documentation files stored in the documentation folder, including `.md` and `.txt` files.
- Gemini API configuration for modes that use the LLM.

**What outputs does DocuBot produce?**

DocuBot produces natural-language answers generated by Gemini, relevant documentation snippets with their source filenames, or a refusal message when the documentation does not provide enough evidence to answer a question.

---

## 2. Retrieval Design

**How does your retrieval system work?**

DocuBot uses a keyword-based retrieval system.

- **How do you turn documents into an index?** Documents are loaded and tokenized. The text is converted to lowercase, punctuation and common stop words are removed, and an inverted index maps words to the documents containing them.
- **How do you score relevance for a query?** Each paragraph is compared with the query. The system counts how many unique query words appear in each paragraph.
- **How do you choose top snippets?** Paragraphs with a score greater than zero are sorted by relevance, and the highest-scoring snippets are returned using the top-k limit.

**What tradeoffs did you make?**

I chose keyword-based retrieval because it is simple to implement and does not require additional models or complicated search techniques. This makes the system relatively straightforward, but it can miss relevant information when different word forms are used. For example, a query containing "generated" may not match documentation containing "generate." Splitting documents into paragraphs can also separate headings from their descriptions, resulting in incomplete context.

---

## 3. Use of the LLM (Gemini)

**When does DocuBot call the LLM and when does it not?**

- **Naive LLM mode:** Sends the entire documentation corpus to Gemini and asks it to answer the user's question without retrieval.
- **Retrieval only mode:** Does not call Gemini. It uses the retrieval system to find and display relevant documentation snippets.
- **RAG mode:** First retrieves relevant documentation snippets and then sends those snippets to Gemini to generate an answer.

**What instructions do you give the LLM to keep it grounded?**

In RAG mode, Gemini is instructed to:

- Answer using only the retrieved documentation snippets.
- Avoid using outside knowledge or making unsupported assumptions.
- Refuse to answer when the retrieved evidence is insufficient.
- Use the refusal message: "I do not know based on the docs I have."
- Include the filenames of the documentation sources used in its answer.

These instructions help reduce unsupported answers and make responses more traceable to the documentation.

**What patterns did you notice?**

- **When does naive LLM look impressive but untrustworthy?**

  Naive LLM can produce fluent and detailed responses, but those responses are not necessarily grounded in the project documentation. For example, when asked how access tokens are generated, it provided a general explanation of OAuth and JWTs instead of explaining the project's actual implementation.

- **When is retrieval only clearly better?**

  Retrieval Only is useful when the goal is to find actual documentation evidence. It successfully retrieved information about access tokens and the users endpoint. However, its results can be difficult to interpret because it returns snippets without generating a complete explanation.

- **When is RAG clearly better than both?**

  In these experiments, RAG did not clearly outperform both other modes in providing a more complete answer. However, it demonstrated an important advantage: it refused to answer unrelated questions and avoided inventing an answer when the retrieved evidence was insufficient. Its effectiveness depends heavily on retrieval quality.

## 5. Failure Cases and Guardrails

**Describe at least two concrete failure cases you observed.**

**Failure case 1: Access token generation**

- **What was the question?** How are access tokens generated?
- **What did the system do?** Naive LLM provided a general OAuth/JWT explanation. Retrieval Only found information about the token system, secret key, and token lifetime but missed the specific generation function. RAG refused to answer.
- **What should have happened instead?** The system should have retrieved the documentation describing the actual token generation process and allowed RAG to explain it using that evidence.

**Failure case 2: Identifying the users endpoint**

- **What was the question?** Which endpoint returns all users?
- **What did the system do?** Retrieval Only returned the paragraph stating that the application returns a list of all users and that access is restricted to admins, but it did not retrieve the associated endpoint heading. RAG could not identify the specific endpoint path.
- **What should have happened instead?** The retrieval system should have preserved the endpoint heading together with its description so RAG could provide the correct endpoint.

**When should DocuBot say "I do not know based on the docs I have"?**

DocuBot should refuse to answer when:

1. The user's question is unrelated to the available documentation, such as asking for the best pizza restaurant.
2. The retrieved snippets do not contain enough information to answer the question accurately.
3. The available documentation does not support the specific details requested, such as an endpoint path that was not included in the retrieved context.

**What guardrails did you implement?**

- A minimum relevance score is required before the system considers retrieved context meaningful.
- The system refuses to answer when no relevant snippets are retrieved or the relevance score is insufficient.
- RAG is instructed to use only the retrieved snippets rather than outside knowledge.
- RAG is instructed to use a refusal message when the evidence is insufficient.
- The system limits the number of retrieved snippets using a top-k setting.

## 6. Limitations and Future Improvements

**Current limitations**

1. Keyword-based retrieval may miss relevant information when query terms and documentation terms use different word forms.
2. Splitting documents into paragraphs can separate headings from their descriptions, resulting in incomplete retrieved context.
3. The relevance scoring system is relatively simple because it counts matching query words rather than understanding the meaning or context of the question.
4. RAG depends on the quality of retrieved snippets and may refuse to answer even when the information exists elsewhere in the documentation.

**Future improvements**

1. Improve keyword matching through stemming or lemmatization so different word forms can match.
2. Preserve Markdown headings and their associated content when splitting documents into snippets.
3. Improve relevance scoring with more advanced retrieval techniques, such as BM25 or semantic search.

## 7. Responsible Use

**Where could this system cause real world harm if used carelessly?**

DocuBot could cause problems if developers rely on incorrect or unsupported answers when working with APIs, authentication, or application configurations. For example, an incorrect explanation of access token generation could lead to security mistakes. Missing documentation or incomplete retrieved snippets could also cause developers to misunderstand how a system works. Users should not assume that a fluent LLM response is automatically correct.

**What instructions would you give real developers who want to use DocuBot safely?**

- Always verify important answers against the original project documentation and source code.
- Do not rely on generated answers for security-sensitive decisions without independent verification.
- Treat refusal messages as an indication that more documentation or context may be needed.
- Keep documentation accurate and up to date so the retrieval system has reliable information to work with.
